기능 명세 · v1

Sojung 재고 · 거래처 관리 서비스

작성일 2026-08-27 범위 전체 기능 정의 및 순서 상태 1단계 구현 착수

사내 재고관리와 거래처 관리(입출금·미납금·선납금)를 함께 처리하는 내부 전용 서비스의 전체 구현 범위를 정리했습니다. 각 기능을 왜 이런 형태로 설계했는지 결정 배경을 함께 남겨, 이후 검토와 변경 요청의 기준으로 삼을 수 있게 했습니다.

배경

  • 회사 사람들만 사용하는 내부 전용 서비스 — 외부 공개나 타사 공유 없음
  • 같은 사내망(LAN)의 컴퓨터끼리만 데이터를 공유
  • 배포 구조: 사내 PC 한 대에 Next.js 서버 + SQLite를 상시 구동하고, 다른 PC는 브라우저로 접속. 클라우드 배포 대신 이 구조를 택한 이유는 "사내 컴퓨터들끼리만 공유"라는 요구를 가장 단순하게 만족시키기 때문
  • 기능은 한 번에 전부 만들지 않고, 아래 순서대로 하나씩 추가

기능 상세

01 재고관리
구현 진행 중

기능

  • 품목 등록 · 수정 · 삭제 — 품목명, 규격, 단위, 분류, 최소재고 기준, 메모
  • 품목별 현재 재고 수량 — 입출고 이력에서 자동 집계, 별도 저장하지 않음
  • 입고 · 출고 · 재고조정 등록 — 날짜, 수량, 단가, 메모
  • 품목별 입출고 이력 조회
  • 최소재고 미달 품목 목록에서 시각적 강조
  • 품목 검색 · 필터

결정 배경

  • 전체 기능 중 재고관리를 1순위로 지정 — 사용자가 직접 우선순위를 정함
  • 단가는 품목에 고정하지 않고 거래(입출고)마다 입력 — 매입·매출 단가가 거래 시점마다 달라질 수 있기 때문
  • 수량은 소수점 허용 — kg, L 등 무게·부피 단위 품목도 다뤄야 하기 때문
  • 거래처 연결은 이번 단계에서 제외 — 2단계(거래처관리) 완성 후 입출고 기록에 연결할 예정
  • 재고 부족 상태에서도 출고 자체를 막지 않음 — 실사 오차 등으로 마이너스 재고가 생길 수 있어, 강제 차단 대신 목록에서 시각적으로만 경고
02 거래처관리
예정

기능

  • 거래처 등록 · 수정 · 삭제 — 상호, 담당자, 연락처, 사업자번호, 매입처/매출처 구분
  • 거래처별 거래 내역(입출고 연동) 조회

결정 배경

  • 매입처와 매출처를 별도 테이블로 분리하지 않고 거래처 테이블 하나로 관리, 구분은 필드(매입/매출)로 처리 — 사용자가 명시적으로 요청한 구조
03 입출금 · 잔액 · 알림
예정

기능

  • 입금 · 출금 등록 → 거래처 잔액 자동 갱신
  • 거래 · 거래처 단위 결제기한 설정, 기한 임박(D-3) · 초과 자동 감지
  • 알림 — 화면 내 목록 + 실시간 배지/토스트 병행
    • 이벤트: 입금·출금 처리됨, 미납 발생, 결제기한 임박/초과, 선납금 발생, 선납금 차감/소진, 잔액 정산 완료
    • 전체 이력 DB 보관, 읽음/안읽음 상태 관리
  • 거래처별 실시간 잔액(미수금/미지급금) = 거래 누적 − 입출금 누적
  • 거래처 원장 화면 — 날짜순 거래 · 입출금 · 잔액 흐름

결정 배경

  • 원래 "입출금 관리"와 "미납/선납금 관리"를 별도 기능으로 나눴으나, 같은 거래처별 잔액 데이터를 공유한다는 지적에 따라 하나의 도메인으로 재구성
  • 알림 형태는 화면 내 목록과 실시간 배지/토스트 둘 다 제공 — 즉시 확인과 사후 확인을 모두 지원
  • 결제기한 개념을 도입 — 단순 잔액 추적만으로는 부족하다는 확인에 따라 거래처/거래별 기한 설정을 추가
  • 알림 이력은 전량 DB 보관(읽음/안읽음 관리) — 감사 로그 성격으로 언제든 재조회 가능하게 함
04 미납금 · 선납금 관리
예정

기능

  • 미납금(외상) 목록 — 거래처별, 기한 임박/초과 상태 표시
  • 선납금(선수금) 목록 — 다음 거래에서 자동 차감

결정 배경

  • 3단계(입출금 · 잔액 · 알림)의 데이터와 계산 로직을 그대로 공유하는 조회 화면으로 설계 — 잔액 계산 로직을 중복으로 두지 않기 위함
05 공통 · 기반
예정

기능

  • 로그인 · 권한
  • 엑셀 · CSV 내보내기
  • 영수증 · 증빙 출력
  • 대시보드 — 오늘의 거래, 재고 부족 품목, 미납금 상위 거래처, 최근 알림 요약

결정 배경

  • 사내 전용 서비스지만 로그인/권한이 필요하다고 확인 — 단순 LAN 접근 제한만으로는 부족
  • 엑셀/CSV 내보내기 필요 — 사용자 확인
  • 영수증 출력 필요 — 거래처에게 "이미 냈다" 또는 "이 물품을 샀으니 이만큼 내야 한다"를 증명할 수 있는 증빙 자료가 실무상 필요하기 때문
  • 이 네 기능은 재고 · 거래처 · 입출금 데이터 위에서 동작하므로, 해당 도메인들이 먼저 갖춰진 뒤 마지막 단계로 배치

아직 정해지지 않은 사항

  • 로그인 방식 — 계정별 로그인인지, 공용 비밀번호인지, 역할(직원/관리자) 구분이 필요한지
  • 영수증 서식 — 사업자번호, 직인 등 어떤 정보가 포함되어야 하는지
  • 대시보드 지표 우선순위 — 어떤 요약 정보를 가장 먼저 보여줄지
현재 1단계(재고관리) 구현을 진행 중이며, 완료 후 DEVLOG.md에 상세 작업 기록을 남깁니다.
